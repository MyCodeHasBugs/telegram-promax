## 二次复读 ("这回呢") — 又新增了房间准入(密码), 再挖出两个小洞
本轮新代码: F3-4 房间密码准入 (create_room / auth room_password, BLAKE3(room||sep||pw)
域分离哈希, 房空即清 room_metadata)。逐行复审后确认根因层仍全绿, 但发现两个此前未列的
**低危 latent bug** (闭环模型下影响小, 但代码注释是错的 / 一旦对外开放会放大):

- 🟡 **N1 房间密码可无限暴力破解 (auth 无限流)**: `auth` handler 里房密码错只 return 不断连
  (server_v2.py:378-385), 注释宣称"连错 5 次/10s 由 rate_log 闸门限制" — **但 rate_log 只在
  relay_message 里消费, auth 从不查它**。即注释描述的限流根本不存在, 房密码可被高速穷举。
  闭环下无第三方故低危; 若开放房间则应在 auth 加独立失败计数/退避。
- 🟡 **N2 签名对 n 只覆盖低 32 位**: 发/收都用 `(int)msgN` 截断做签名输入 (ChatSessionV2.cs:316,517)。
  明文 MITM 可把 envelope.n 加 2^32 的整数倍而不破坏 Ed25519 验签 → 收方 ratchet 见巨大 gap →
  GapTooLarge 丢包 (仅 DoS, 且仅明文链路)。修复: 签名输入用完整 8 字节 long, 或截断前校验 n 范围。
- create_room 可在活跃"公开房"名上盖章设密码成为 owner (existing=None 直接写) — 闭环无影响。
